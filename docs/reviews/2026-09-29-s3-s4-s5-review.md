# S3–S5 pre-S7 deviation review

Reviewed `main@1af25ae`, including the observation-version S3 additions in
`7b9f4ab`. This is a read-only code review: the review commit changes no
implementation. The locked SRS and HLSA decide requirement ownership; the
working LLD and technical investigation are used only to identify departures
from the current design and research direction.

## Result

Not ready to treat the M1–M2 path as a clean S7 input. Two high-severity
findings should be fixed before S7 depends on the observation contracts. The
model scalar path, most stage boundaries, and the pressure-aware profile wire
contract are otherwise sound for their implemented scope.

## High-severity findings

### H1 — persisted markers can be synthetic and geographically wrong

**Tag: CONTRADICTS-LOCKED**

`ingestion/storage/postgres.py:273-285` groups a profile, chooses its earliest
timestamp, and independently averages every latitude and longitude. That tuple
need not be any source observation. It is especially wrong across the
antimeridian: a profile at 179° and -179° is persisted at 0°. S4 then declares
that the S3 marker coordinates were not averaged at
`processing/observation.py:42-49`.

This can place the marker in the wrong ocean and make the PostGIS bounding-box
lookup omit or return the wrong profile. It contradicts IDO-001's
geospatially-accurate-marker requirement and the HLSA requirement that S3 keep
observation context available to S4 without changing its meaning.

Evidence: a two-row profile with longitudes 179° and -179°, latitudes 8° and
10°, produced a persisted marker at longitude 0°, latitude 9°, paired with the
first timestamp.

Required correction: choose and retain one complete source row under an
explicit representative policy, including its source index, or introduce an
explicit derived-marker contract and provenance. Do not average signed
longitude naively, and do not describe a derived position as source-exact.

### H2 — expected observation failures become `internal_error` HTTP 500

**Tag: DEPARTS-LLD-OR-RESEARCH**

The common mapping at `processing/execution.py:106-128` omits
`ObservationIdentityError`, `ObservationVariableError`,
`ObservationValidationError`, and `AllMissingObservationError`.
`serving/observations.py:89-97` sends every builder exception through that
mapping, so ordinary observation outcomes are classified as unexpected server
faults. For example, `processing/observation.py:917-923` raises a typed
unavailable-variable failure, but the public route returns HTTP 500 with
`internal_error`. A valid empty marker search is handled the same way.

This departs from working LLD §§5–6, where unsupported/not-found observation
requests have explicit reasons, and from the investigation's rule that
out-of-range or all-missing work becomes typed state rather than an empty or
opaque response. S7 cannot distinguish an empty search, unsupported variable,
invalid stored observation, or genuine server failure.

Evidence through the HTTP adapter:

- unknown requested profile variable → HTTP 500 / `internal_error`;
- a valid bounding box containing no profiles → HTTP 500 / `internal_error`;
- missing S3 version → HTTP 404 / `data_unavailable` (the existing correctly
  mapped comparison case).

Required correction: define stable observation-specific failure codes and HTTP
semantics, add them to the shared mapping in specificity order, and cover every
typed observation error at the S4 and S5 boundaries.

## Medium-severity findings

### M1 — pressure extents are still published as depth extents

**Tag: DEPARTS-LLD-OR-RESEARCH**

Agent C's descriptor correctly derives `vertical_kind="pressure"` from
decibar units (`ingestion/query.py:447-465`), but the shared extent contract
has only `depth_min` and `depth_max` (`ingestion/query.py:75-86`). The write
path stores every vertical coordinate under those names
(`ingestion/storage/postgres.py:216-219,255-257,283-284`), and
`ObservationVersionDescriptor` exposes that same `DatasetExtent`
(`ingestion/query.py:468-490`). S5 therefore publishes an internally
contradictory descriptor such as `PRES`, `decibar`, `pressure`, alongside
`depth_min` and `depth_max`.

No numeric pressure-to-depth conversion occurs in the S4 profile product, which
is correct, but catalogue consumers can still label or filter pressure as
depth. The research contract requires an explicit vertical-coordinate type,
and the review criterion forbids treating pressure as depth.

Required correction: make catalogue vertical extents semantic (for example,
`vertical_min`/`vertical_max` plus kind and units), or use distinct typed depth
and pressure extents. Preserve backward compatibility explicitly rather than
silently reinterpreting existing fields.

### M2 — observation-catalogue outages are returned as successful null data

**Tag: DEPARTS-LLD-OR-RESEARCH**

The model catalogue path returns a coded HTTP 503, but an exception from
`list_observation_versions` is caught at `serving/http.py:126-137` and rendered
as HTTP 200 with `observation_versions: null` and an empty
`observation_unavailable` list. There is no failure code or reason and the
typed `Catalogue` protocol at `serving/http.py:36-39` does not declare the
observation operation at all.

This makes “catalogue unavailable” indistinguishable from an optional or
partially implemented response and departs from the LLD control path's explicit
failure contract. Return a typed/coded partial failure or fail the catalogue
request consistently; also represent observation listing in the public
catalogue protocol instead of discovering it with `getattr`.

### M3 — the S3-record handoff drops source encoding metadata

**Tag: DEPARTS-LLD-OR-RESEARCH**

The S3 `ObservationProfile` contract carries values, masks-by-`None`, units,
QC vocabulary, and timestamps, but not the original value/QC dtypes or time
encoding. Consequently the S4 record adapter fills coordinate dtypes and time
encoding with `None` at `processing/observation.py:772-803` and fills variable
and QC source dtypes with `None` at `processing/observation.py:933-945`.
The binary layout declares the reconstructed delivery dtype, so bytes remain
self-describing, but the source encoding cannot be audited from the product.

This is honest absence rather than invention, and source data remains
recoverable in S3, but it falls short of the working LLD's product-envelope
encoding requirement and the investigation's data-type manifest. Extend the S3
profile contract with the available source dtype and time encoding, keeping
absence explicit for legacy records.

## Low-severity quality findings

### L1 — baseline strict-zip and type-boundary debt remains

**Tag: QUALITY**

Scoped production code still has `zip()` without `strict=` at
`processing/observation.py:536,630`, `processing/point_field.py:77`, and
`serving/wire_observation.py:201`; Agent C's S3 extraction also has one at
`ingestion/storage/query.py:811`. Present builders normally derive paired
arrays from one validated dimension, so no current mismatch was reproduced,
but a later contract change could silently truncate instead of failing.

The principal type-erasing sites are the model-only `Catalogue` protocol plus
dynamic observation lookup (`serving/http.py:36-39,126`) and the `Any`-typed
observation execution shim (`serving/observations.py:89-97`). Ruff and mypy are
not installed in the repository virtual environment, so the baseline lint/type
counts could not be re-measured without changing the environment. These sites
should be tightened when the high findings are fixed.

## What is correct

- HLSA ownership is otherwise preserved. S4 produces scientific products, S5
  validates/translates requests and serves them, and no S4/S5 core workflow
  imports a PostgreSQL, object-store, cloud, or renderer implementation.
- Concrete S3 construction occurs in `serving/compose.py:78-95`; core paths
  receive query, builder, executor, catalogue, and observation contracts.
  Backend selection does not leak into processing or HTTP workflows.
- Agent C's `ObservationVersionDescriptor` is resolved per request, so API
  instances can serve versions imported after startup. Unknown CRS, vertical
  direction, basis, or depth/pressure units are refused rather than guessed.
- Exact managed profiles retain dataset version, platform, cycle, source-order
  vertical values, variable values, variable/vertical units, timestamps,
  missing masks, QC flags/vocabulary, provenance, CRS, and vertical direction.
- Pressure is not numerically converted or relabelled inside the S4 profile
  product or observation wire format: `vertical_kind="pressure"` and
  `decibar` survive the S3→S4→S5 path.
- Model point fields select source cells without inventing values. Sampling is
  declared and traceable to source indices; masks, units, coordinate roles,
  CRS, vertical direction, physical ranges, transforms, provenance, and loss
  metadata travel in the product envelope.
- Depth slices operate independently on decoded scientific values. Exact
  selection and optional linear interpolation are explicit, source levels and
  weights are recorded, and missing bracketing cells remain masked.
- S5 separates JSON descriptors/status from aligned binary arrays. The wire
  layout declares names, roles, dtype, byte order, offsets, lengths, masks, and
  source indices; supported numeric arrays are not quantized.
- Observation serving retains no request/job state. Repeating the same request
  against an immutable version rebuilds the same product and byte payload, so
  multiple API instances do not require shared observation session state.
- Unexpected failures are logged while storage paths, DSNs, and credentials
  are withheld from public error messages.
